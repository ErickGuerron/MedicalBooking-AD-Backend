## Specs
- S1: User decision: option A from the scope question: REST gaps 1 to 4 of the backend gap list (users listing, knowledge listings, order and appointment listings, shadow edit history). SOAP (E6) is out of scope and stays for later. Each listing is a new route; no existing route changes its behavior or response.
- S2: Spec 6 row "Usuarios": GET /api/v1/users next to the existing POST /api/v1/users. Requires usuarios.administrar. Returns id, email, nombres, apellidos, activo and roles, ordered by email. ASSUMPTION: optional query limit (default 50, max 200) and offset (default 0); invalid values answer 422.
- S3: Spec 6 row "Conocimiento": GET /api/v1/knowledge/rules. ASSUMPTION: conocimiento.leer sees only VALIDADA rules; conocimiento.validar or conocimiento.administrar also sees BORRADOR rules. Optional query estado (BORRADOR or VALIDADA). Drafts are visible only to those roles; no response ever exposes a draft to conocimiento.leer alone.
- S4: GET /api/v1/knowledge/references?analito_id=&estado=BORRADOR|VALIDADA, for drafts visible to conocimiento.validar or conocimiento.administrar. Lists the reference ranges with their fields and state. ASSUMPTION: analito_id is required when estado is BORRADOR; the existing GET /api/v1/knowledge/analytes/{id}/references keeps returning only validated ranges valid on a date.
- S5: Spec 6 row "Órdenes": GET /api/v1/lab/orders lists orders the actor may read. ASSUMPTION: a PACIENTE sees own orders; a doctor with a doctor profile sees orders he or she ordered; any other actor gets 403. Optional query estado and the same limit and offset rules as S2. Each row carries id, paciente id, estado and fecha; no result values appear in the list.
- S6: GET /api/v1/appointments lists appointments the actor owns. ASSUMPTION: a PACIENTE sees own appointments; a doctor sees appointments of his or her agenda; any other actor gets 403. Optional query estado and the same limit and offset rules as S2. Rows carry id, estado, inicio and fin in ISO-8601 UTC, and never another patient's data.
- S7: GET /api/v1/lab/orders/{id}/sombra/snapshots/{snapshot_id}/hallazgos/{hallazgo}/ediciones returns the append-only edit history of one shadow finding (table hallazgos_sombra_ediciones, migration 0016). Same access as GET /api/v1/lab/orders/{id}/sombra: permission resultados.leer_con_acceso and ordering-doctor ownership; missing and foreign resources answer 403 with the same body. Every read is audited with its outcome. Edits are never modified by this endpoint.
- S8: Every new route is documented in the OpenAPI contract (docs/api/openapi.json regenerated) and in README endpoint table. Unit tests pin each rule; integration tests cover each route's 200/403/422 paths against SQL Server.
- S9: Old behavior protected: the existing POST /api/v1/users, GET /api/v1/knowledge/analytes/{id}/references and GET /api/v1/lab/orders/{id} keep their current responses.

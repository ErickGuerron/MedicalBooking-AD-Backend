## Specs
- S1: User decision: "desde develop saca otra rama para hacer dichas implementaciones" (scope: invoices and checkout endpoints of spec section 6). The webhook is already on develop (merge aa0a458): verify it, do not change it.
- S2: Spec 6: POST /api/v1/invoices (create a factura for an appointment), POST /api/v1/payments/checkout (start a payment for a factura). Business endpoints require JWT and per-resource authorization.
- S3: Spec 7.3: checkout uses an idempotency key and keeps attempt/status records; a payment is never confirmed by a browser redirect (only by the verified webhook, already implemented); no DB transaction stays open while the provider is called.
- S4: ASSUMPTION: the patient who owns the appointment creates its invoice and pays it (permission facturas.crear and pagos.iniciar granted to PACIENTE by migration 0018). Ownership is checked in the application layer. Other roles get 403.
- S5: Missing and foreign appointments/facturas return the same 403, so identifiers do not leak (same rule as E2 and E3).
- S6: An invoice has one detail line: the medical service price (servicios_medicos.precio_base, moneda), subtotal = total, impuestos 0 (ASSUMPTION: no tax rules in the spec). Invoice numero_factura is generated by the server, unique.
- S7: An invoice can be created only for an appointment in PENDIENTE_PAGO or CONFIRMADA. Only one invoice per appointment: the application checks it (409) and the unique filtered index UX_facturas_cita (migration 0018) is the last guard against concurrent requests.
- S8: Checkout body: { "factura_id" }. Header Idempotency-Key required (8 to 100 characters, same rule as E2). A new key creates one pagos row (PENDIENTE, clave_idempotencia = key) and one Stripe Checkout Session; the session id is stored. The same key with the same factura returns the same checkout (200, replay); the same key with another factura returns 409.
- S9: The factura must be PENDIENTE and owned by the actor; a paid or cancelled factura returns 409.
- S10: Stripe Checkout Session is created through the Stripe HTTP API with the stripe_secret_key setting (STRIPE_SECRET_KEY in .env, never logged) and the Stripe Idempotency-Key header. Without the secret the endpoint answers 503 and creates nothing (fail closed).
- S11: The provider call happens outside any DB transaction (spec 7.3): reserve the pagos row, call Stripe, then record the session id. If the provider fails, the pagos row is marked RECHAZADO and the response is 502-class error mapped to 503 (ASSUMPTION: 503, no 502 in the shared error set).
- S12: Responses use the standard JSON problem format (type, title, status, detail, correlation_id).
- S13: DoD (spec 13): permission checks, unit and integration tests, error coverage, README and OpenAPI documentation.
